# 验收判据的防假通过加固

## 核心命题

**「全绿」最危险的时刻不是失败，而是验的根本不是这份代码 / 测的东西根本不存在。**

判据自身也是代码，它会出错，而且出错时输出的结论**看起来很像真的** ——
这比直接报错耗人得多：人会去查服务、查构建、查数据，而真正的原因在判据自己的参数里。

## 动手前：先证明判据能抓到问题

**任何判据改动，先做反证测试**：造一个「应该失败」的场景，确认它真的失败。

```bash
# 造一份「旧版/错误版」的服务或数据，让判据跑一遍
cp -r ./site /tmp/fake && cd /tmp/fake && sed -i 's/new-class/old-class/' index.html
# 起服务 →跑判据 → 必须失败，且失败信息要指出「哪里是旧版」
```

只跑正例= 没验判据。反证必须做到「输出结论与真实原因对应」，
如果判据报错的原因与实际注入的问题不符，说明判据本身有 bug。

## 六类结构性假通过（逐个查）

| 类型 | 症状 | 修法 |
|---|---|---|
| **测的对象不存在** | 循环体一次没跑 → 报「全绿」 | 空集合时改报「本轮无可查」，不要报通过 |
| **服务/环境不是这份** | 端口上跑的是旧实例，判据全绿 | 开工前加**身份预检**（见下） |
| **清单永远命不中** | 硬编码清单里某项已从源头删除，无任何提示 | 改成**自动扫描** + 实测零引用 |
| **判据自己写错** | URL 拼错、路径重复、选择器写错，输出却像真结论 | 加**静态自检**，在跑之前拦下 |
| **状态类判据写死值** | 上一组已把状态改了，本组仍断言旧值 → 误报「功能丢失」 | 动态取反 / 从当前状态推导期望值 |
| **等待不够** | 测「已完成」而代码有兜底定时器 | 等待 > 兜底定时器 **+ 一帧最坏延迟** |
| **白名单「定义了」≠「被使用了」** | 查「白名单字典存在」就报绿，把**使用点**改回硬编码也照样绿 | 见下「第七类」专节 |

## 第七类：常量/白名单的「存在 ≠ 被使用」（最隐蔽）

判据写成 `assert "ALLOWED_X" in code` 就通过，但代码里那个**常量定义了却没人用**，
真正的执行点仍走老路径 —— **判据恒真，无法区分好坏实现**。

**实测案例**：`cnt()` 的 SQL 白名单改造加了三条判据，全部只查「字典 `_CNT_STMT` 存在」。
把使用点 `stmt = _CNT_STMT[kind]` 改回硬编码 SQL，字典仍在文件里 → **三条全 PASS → 白测**。

**修法：查真实使用点，不只查定义。**

```python
# ✗ 恒真：删掉使用点它照样绿
check("_CNT_STMT" in code, "走白名单式参数化")

# ✓ 抓函数体，确认真的按白名单取值
m = re.search(r"def cnt\((.*?)\)\s*:(.*?)(?=\n    def |\ndef |\nif __name__)", code, re.S)
check(m and "_CNT_STMT[" in m.group(0), "cnt() 真的按白名单取值")
# 再补：白名单键是否齐全
for k in ("all", "pending", "rejected"):
    check('"%s"' % k in code.split("_CNT_STMT")[1][:400], "白名单含 %s 分支" % k)
```

**通用判据**：`A 存在` 与 `B 用到 A` 是两件事。凡是判据只查前者，就必须补后者；
或反证时**专门改使用点**（保留定义）再跑一次，确认会红。

## 身份预检（最值得加的一段）

任何「起服务 → 跑判据」的流程，都该在判据之前确认服务身份。三条独立判据：

```js
// 1) 服务可达（带重试，非2xx 也重试，递增退避）
// 2) 服务的是「这份」而非别的实例 —— 取一个只有这份才有的标记
//    （如部署前缀、版本化类名）
// 3) 服务的是「当前版本」而非旧版 —— 取一个「刚改过的特征」双向比对：
//    既要有新标记，也不能有旧标记（只查「有新版」会漏掉「改一处漏一处」）
```

★ 标记要选那种**「改了就一定变、没改就一定不变」**的字符串：
- 用「页面上出现过的东西」会漏（静态资源里没进 HTML）
- 用「版本号」需要额外维护、迟早忘记更新
- 用**刚改过的类名/函数名**最实

★ 预检请求要走 `127.0.0.1` + 显式 `Host` 头，不要用页面用的主机名：
浏览器的 `--host-resolver-rules` 映射**只对浏览器生效**，Node/Python 侧会真去做 DNS → 超时。

## 静态自检（把「判据写错」变成启动失败）

判据里凡是「拼接路径 / 拼字符串」的调用，加一段扫描：

```js
(function selfCheck() {
  const src = fs.readFileSync(new URL(import.meta.url), "utf8");
  const bad = [];
  for (const m of src.matchAll(/get(?:Retry)?\(\s*["'`]([^"'`]+)["'`]/g)) {
    if (m[1].includes(PREFIX)) bad.push(m[1]);   // 已拼过还再拼
  }
  if (bad.length) { console.error("【自检失败】" + bad.join(", ")); process.exit(2); }
})();
```

要点：
- **在启动浏览器 / 起服务之前**跑，失败要快、退出码要区分（如 2=自检失败）
- 正反两侧都要测：正常路径通过、故意写错被拦

## 清理脚本的加固

**零引用判据**：
- 两种形态都查：完整文件名 **+** 去扩展名的 stem（CSS/JS 里常只写 stem）
- 保留白名单：`favicon*`（浏览器自动请求，删了标签页退回默认图标）、
  构建产物目录、`.well-known/`（给外部客户端读的，不是页面资源）
- **反证**：造一个「看着像孤儿但被 `url()` 引用」的文件，确认不被删
- **第二道保险**：后续步骤的引用校验必须能报出「引用指向不存在的文件」

**清单 vs 自动扫描**：硬编码清单会随每次改动腐烂，且「清单漏了新条目」是**静默**的。
能扫就扫，扫不了才列清单（并列清单时要标注「新增项需手工补」）。

**静默失效的提前返回**：
```python
if not os.path.isdir(GAME_DIR):
    return 0        # ← 这会把后面所有步骤一起跳过，且无任何提示
```
凡是「提前 return」的地方都要问：**后面的步骤是不是也被跳过了？**
正确写法是只跳过依赖该目录的步骤（`if files:` 包住），并把结论表述改成
「本轮无可查」而不是「已确认无残留」。

## 退出码与清理

- **不要用 `process.exit(1)` 做预期内的中止**：它**立即**终止，
  `finally` 里的进程清理 / 临时目录删除都不执行 → 留僵尸进程，
  下一次跑开始出**新的假失败**。改抛哨兵错误（如 `PRECHECK_FAILED`），
  由 `catch` 静默收尾，末尾统一 exit。
- 每次跑之前 `taskkill` 残留浏览器；连续失败时**换端口 + 换临时目录**，
  不要用同样方式重试。

## 失败表象与真实原因错位（把「表象」当「结论」会白修）

流水线里某步抛异常，脚本就在末尾打「XX 失败」—— 但**失败的那一步往往不是出问题的那一步**。

**实测案例**：打包脚本 `[4/5] 输出` 段先 `os.remove(旧包)` 再 `copy2(新包)`。
签名已成功，但删旧包失败（文件被占用 / 安全层拦截批量删除）→ 抛异常 →
脚本打印「打包失败」，而桌面上的包**根本没更新**。
排查时极易误判成「签名链路坏了」，去查根本没问题的那部分。

**修法**：
- **非关键步骤的清理失败不得中断流程**，改为 `try/except` 后继续（本例直接 `copy2` 覆盖即可）。
- 报错时打印**具体步骤名与已通过的证据**（如「签名已 verified，请检查输出阶段」），
  不要只给一个笼统的失败标签。

## 收尾自检模板

```bash
# 语法
node --check x.mjs || python -c "import ast,io; ast.parse(io.open('x.py',encoding='utf-8').read())"
# 测试痕迹
grep -c "test-\|debug\]\|zzz" x.*            # 应为 0
# 括号/花括号配平（仅对非压缩代码有效）
# 真解析器验证资产（XML/JSON/JS）—— 计数法对压缩代码无效
```

★ 「测试痕迹为 0」这条容易漏：反证测试留下的 `zzz-test-*` 文件、
临时 debug 输出，混进交付物里别人会以为是有意为之。

## 第八类：判据的「工作目录」坏了，输出仍像真结论

判据跑在错误的目录里 → 命令本身报`not a git repository` / `找不到文件`，
但**如果判据用 `||` / `try` 兜住了错误，就会把「查不到」输出成「一切正常」**。

**实测案例**：批量检查 `.gitignore` 是否生效，用 `git check-ignore -q "$f"` 判断，
前置工作目录跑到了父目录 → `git` 对每个文件都报 `not a git repository`，
判据把这个当成「未被忽略」→ **6 个文件全报「入库」，其中包括密钥库**。
结论看起来极其合理（而且方向是「危险的那一侧」），却是彻底错的。

**修法：**
- **跨目录一律用 `git -C <绝对路径>` / 绝对路径调用工具**，不要依赖 shell 的当前目录。
- 判据里**显式检查工具自身的前置状态**，例如先跑一次必然成功的探针：
  ```bash
  git -C "$REPO" rev-parse --git-dir >/dev/null 2>&1 || { echo "判据前置失败：不在仓库内"; exit 2; }
  ```
- ★ **并行/串行调用 shell 时，前一条命令的 `cd` 会影响后一条的初始目录**。
  这是本机最容易复发的坑 —— 表现为「上一轮还好好的，这轮全错」。

## 第九类：同一个症状连续出现时，先怀疑「自己的输入没变」

外部操作（合并 PR、推接口）连续两次报同一个错时，**先确认第二次真的发出去了不同的内容**，
而不是立刻归因于外部状态变化。

**实测案例**：PR 合并连续两次返回 `Head branch was modified`。
真实原因有二，且**两次完全相同**：
1. 字段用错：`sha` 要的是**head 分支 sha**，我传的是 `refs/pull/1/merge` 的 sha；
2. 修正后的新 JSON 写到了当前目录，而 `--data-binary` 读的却是另一处的旧文件 → 发出去的仍是错值。

**修法：**
- 请求体**一律写文件再传**（`--data-binary @body.json`），避免 shell 破坏引号/换行；
- 改完请求体**回读确认**（`Read` 一次或 `cat` 一次）再发；
- 失败时打印**实际发出的关键字段前 7 位**，而不是只看报错误差文本。

## 第八类补充：外部返回不自洽时，不要猜

`DELETE` 返回 404 但资源仍在列表里 —— 这种矛盾结果说明**你对语义的理解有错**，
不是「网络抖动」「有延迟」。正确做法是换一条**语义确定且无歧义**的路径
（如 `PATCH state=closed`），并同样回读验证最终列表，
而不是把矛盾结果原样报告给用户。

## 汇报纪律

交付时要说清：**判据本身改了什么、判据的正反两侧是否都实测过。**
只报「30/30 通过」而不提「预检抓到了旧实例」，
读者无法判断这个 30 是不是真的。
